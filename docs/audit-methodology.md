# 代码审计方法论 — 从 SoniScope v1.0 审计里程碑提炼

> 提炼自 SoniScope v1.0 审计里程碑(审计基线 `5927f36`),整理日期 2026-07-06。本文是可复用的通用审计方法论指南,文中的具体数字与文件名均为该次审计的案例引用。

## 一、审计是什么

审计不是找茬,是在不改动被审对象的前提下,产出一份"可信、有证据、分级明确"的判断,回答三个问题:哪里不一致、哪里有债务、有什么风险。

好的审计有四个本质特征:

1. **审计是取证工作,不是印象工作。** 每条结论必须能回溯到具体证据(`path:line @ <SHA>`),任何人可用 `git show` 独立复核。没有证据的判断不配进报告。
2. **审计是全覆盖声明,不是抽样巡视。** "查过了"必须可验收——本次实践:63 个代码对象 × 9 个关注面、198 条文档声明、41 个测试模块 × 8 面,每个格子都有下落,包括显式的"已检查,无发现"。
3. **审计的产出是可执行的 backlog,不是评语。** 每条发现带严重度、行号证据、修复建议、工作量档位、上线判定——下一个里程碑拿到报告就能直接排期开工。
4. **审计对"没问题"同样负责。** 本次实践中,config.js 深核零 drift、FC↔Worker 主链零漂移、9/9 错误码有测试覆盖——"清白证明"和问题发现同等重要,它们防止修复阶段误"修"好的东西。

## 二、方法论总纲:六条核心原则

### 1. 标尺先行(Charter First)

在收集任何证据之前,把全部度量标准定稿成章程,且不留自由裁量空间。

章程(CHARTER.md)在第一阶段就锁死:基线 SHA、证据格式、五级严重度(每级绑定项目场景锚点,如 CRITICAL = "数据丢失/有效凭证泄露/认证绕过")、S/M/L/XL 工作量分档、九字段发现 schema、扫描排除清单、秘密红线。全文禁止"视情况""可酌情"类措辞。

为什么有效:多阶段、多执行者并行审计,终点校准时 40 条分散产生的定级横向对照后零调整——锚点体系真正锁住了口径。反之,标尺模糊会让并行执行者各有一把尺,校准成本剧增。

### 2. 基线钉定 + 零 diff 红线

审计对象钉在一个 commit SHA 上,全程不许改动;取证只从 `git show <SHA>:<path>`,禁止读工作树。

- 证据免疫 HEAD 推进:审计文档不断提交,但行号证据永远有效
- 零 diff 验证命令写死(`git diff --stat <SHA> -- <被审目录>` 必须为空),每阶段收尾必跑必记,污染可定位到阶段
- 无例外协议:哪怕发现泄露的有效凭证,也只进台账标 BLOCKER,不中断审计、不动云端、不"顺手修"

### 3. 证据与判断分层

数据流是一条单向管道:

```
工具扫描输出(scans/,线索池)
  → 人工逐条核实三态销号(确认/误报/移交)
    → 发现台账(findings/,九字段 schema)
      → 校准判定(CALIBRATION.md,经批准)
        → 最终报告(REPORT.md,零新判断的机械组装)
```

每层只做自己的事:扫描档案只存档不判断;台账只登记经核实的事实;判断集中在单一经批准的校准文件;报告组装时判断类字段唯一取自校准文件、定位类字段机械抽取台账——验证者可以跨文件逐项比对证明"报告零新判断"。

### 4. 一切完成判定走机械对账

"查完了"不能靠声明,要靠可复算的等式。实例:

- 线索分流:`25 HYP + 4 DNF = 29 条源线索`(附机械计数命令)
- 扫描销号:每档 `确认 + 误报 + 移交 = 命中总数`(五档合计 15+243+0=258)
- 判定覆盖:`12 个分歧格 = 5×1 + 1×7 条发现`(一对多映射显式写出)
- 收尾:报告内嵌 8 项门禁的命令 + 实际输出 + ✓

配套技巧:每类条目用唯一行首锚(`^### F-`、`^| HYP-`、`^### CL-`)供 grep 机械计数;台账初始值全填"待审",收口用 `grep -c '待审'` = 0 证明全覆盖。

### 5. 静态判据为主,执行佐证为辅

契约/一致性判定以代码文本为准;执行证据只用来支撑严重度和归类,不替代静态判据。

执行佐证的纪律:跑在仓外基线副本上(`git archive` 导出或 `git worktree add`)、脚本首部加 `__file__` 来源断言防误 import 工作树、时区敏感用例显式 TZ 双跑、样本"先写预期后实测"防结果倒灌、非生产环境的性能数字通篇标注"非真机,量级参考"。

### 6. 线索假设化,闭环可追溯

前期收集的所有疑点先转成"未验证假设"(HYP),不当结论;审计过程逐条证实/证伪/细化,最终全量闭环。

- 假设是可证伪的陈述,不是答案;复合假设拆半句回填("细化"状态承载部分证实)
- 允许证伪:假设被实测推翻后,按缩窄后的实态立条,不按原表述立条
- 故意设计预分流进 Do-NOT-fix 登记表,不占验证工作量,且防止修复阶段误"修"
- 终点有追溯映射表:发现 ↔ 线索 ↔ 需求三向闭环,含"已检查无发现"的显式行

## 三、怎么审计:五阶段流程

| 阶段 | 做什么 | 关键产物 |
|------|--------|----------|
| 1. 章程与基线 | 钉 SHA、定标尺、线索分流 | CHARTER、假设清单、Do-NOT-fix 预录入、分维度台账骨架 |
| 2. 契约一致性 | 逐字段漂移矩阵(多端多列,每格 agree/diverge/absent/n-a + 行号)、往返校验执行佐证、四类判定(良性/潜伏/活跃失配/覆盖洞)+ Postel 宽严分析、重复逻辑普查 | 漂移矩阵、契约类发现、跨语言契约测试配方 |
| 3. 代码与工具链深潜 | 全量对象登记 × 多关注面普审 + 深挖点;工具扫描存档 + 命中逐条三态销号;债务三要素裁定(结构必要性/兜底机制/漂移后果) | 覆盖台账、扫描档案、代码/工具链发现 |
| 4. 文档与测试审计 | 以代码实态为基准:文档声明四态销号(agree/drift/dead-ref/无法静态核实);测试模块多面台账 + 反向映射(每条既有发现反查测试兜底)+ 门禁三方对照(声称×静态配置×实跑);假设全闭环 | 文档声明清单、测试台账、文档/测试发现 |
| 5. 校准与报告 | 跨维度对齐扫描、真重复判定、根因聚类、修复工作包、三级上线判定准则 + 逐条判定 → 用户批准 → 机械组装报告 | 校准台账、最终报告 + 追溯/聚类附录 |

流程设计要点:

- **依赖编排:** 证据收集阶段(2/3)只依赖章程可并行;文档/测试审计(4)需要代码实态输入;校准报告(5)收官。并行写入靠"台账按维度分文件"防冲突,共享登记表的裁定列留给收口计划统一回填。
- **判断的时序:** 状态词(静态事实)先落格封版,归类(影响判断)后置回填——防判断预设污染证据抽取。
- **人工介入最小化但关键:** 全里程碑实质人工判断点仅 3 处——第三方工具包合法性批准 ×2、校准批复 ×1(多组内容合并单次呈报)。凡能表述为 grep/比对的核验,最终都不需要人。

## 四、工具箱

| 用途 | 工具/命令 | 纪律 |
|------|-----------|------|
| 取证 | `git show <SHA>:<path>`、`git grep -n <pat> <SHA> -- <dir>` | 唯一合法取证方式;工作树取证 = 篡改证据链 |
| 污染报警 | `git diff --stat <SHA> -- <被审目录>` | 每阶段收尾必跑,期望空输出 |
| 静态分析 | 既有门禁(mypy/ruff)+ 扩展规则集、vulture、eslint | 输出只是线索池(本次 94% 是误报);逐条人工核实,禁批量定性 |
| 秘密扫描 | `git grep -nE <五类凭证模式> <SHA> -- .` | 穿透所有排除目录;输出经管道剥离内容列;命中 ≠ 发现 |
| 执行佐证 | `git archive <SHA> \| tar -x` 或 `git worktree add`;钉版运行(`--frozen`) | 仓外副本 + 来源断言 + 用毕拆区 |
| 覆盖率 | 临时注入(如 `uv run --with pytest-cov`)、运行时内置覆盖率 | 数字仅作证据归档,禁作质量评分(负向 grep 守门) |
| 临时包引入 | `uvx <pkg>`、`npx --yes <pkg>@<ver>` | 引入前人工批准 + 预设兜底方案;零仓库配置写入 |
| 环境隔离 | 环境变量指向仓外目录(如 `UV_PROJECT_ENVIRONMENT`)+ `--frozen` | 防包管理器隐式创建 venv / 刷新 lockfile |
| 机械验收 | 行首锚 grep 计数、awk 区间检查、负向 grep(裁量措辞/评分词/秘密模式零命中) | 行首锚定防自指计数 |

## 五、需要注意什么(踩过的坑)

证据纪律类:

1. **秘密红线是绝对的** —— 凭证类证据只写 `path:line + 模式名`,值本体哪怕已过期也不复制(审计文档入 git 即永久,复制即二次泄露);入口脱敏管道 + 出口反扫双保险。
2. **研究/勘察阶段的行号和计数只能当起点** —— 实践中行号偏差、计数误差反复出现,全部以基线实测为准。"以实际为准并如实记录"要写成计划的标准授权条款。
3. **文档声明不能当证据** —— 项目文档的声称可能被代码实态完全推翻;文档与实态的矛盾本身是发现素材,但要归入正确维度裁决。

机械对账类:

4. **自指计数是顽固缺陷** —— 对账命令写进被统计的文档,命令原文自身会被计入(三个阶段各现一次);对策:行首锚定、字符类拆字(`/完成判[定]/`)、或显式注明自指份额。
5. **零命中 ≠ 零存在** —— 字面 grep 在有中间变量的代码上系统性漏报(`require(VAR)` 查不到 `require.*path/`);检索方法本身要按实态修正并写进台账防复踩。
6. **占位词要与收口 gate 协同设计** —— "待审/补证中"只许出现在表行单元格,说明文字零出现,收口负向 grep 才可用。

判断分寸类:

7. **diverge 指语义分歧,不是字面差异** —— 两侧有文档化约定的字面差异是 agree;机械判 diverge 制造伪发现。
8. **重复实现 ≠ 债务** —— 跨部署单元无法共享是结构必然;三要素框架(结构必要性/兜底机制/漂移后果)裁定,"不构成债务"也是带理由的正式下落。
9. **同根因聚合立条** —— 多处命中同一根因合并为一条发现(修复要的是"一个根因一个工单"),但对账等式要显式给出覆盖映射。
10. **严重度按锚点对号,不按字面惊悚度** —— 过期临时凭证入库是 MEDIUM(泄露习惯风险锚),不是 CRITICAL(有效长期凭证锚);容器内 0.0.0.0 绑定在网关语境下不成立发现。

流程协作类:

11. **多计划共担的需求留收尾统一销号**,并行 worktree 计划不碰共享簿记文件(否则簿记滞后/合并冲突)。
12. **worktree 隔离有边界** —— 未跟踪文件在 worktree 里不可达、工具 shim 可能缺依赖;计划引用的上下文必须已提交。
13. **上游留的去向指针,下游要主动闭环** —— 即使计划文件清单没列那个文件。
14. **判断演变用追记不改写** —— 降级/推翻前序初判时追记"人工核实下落 + 理由",保留完整审计轨迹。

## 六、一句话总结

好的审计 = **先定标尺(章程锁死口径)→ 钉住基线(证据免疫变化)→ 分层流水(线索→核实→判断→组装,层层可复核)→ 机械对账(完成判定可复算)→ 闭环追溯(每条线索有下落,包括"无发现")**。

它的成功标志不是找到多少问题,而是:任何人拿着报告能独立验证每一条结论,拿着 backlog 能直接开工修复,并且确信"没写进报告的地方,确实查过了"。
