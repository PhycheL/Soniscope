> 在 `requirements_v4.md` 基础上，修正幂等判断与重转触发机制：正常轮询以 `.done` 标记为准，不再因配置变更自动全量重转；四元组降级为溯源 + CLI 筛选用途；存量重转必须通过 `retranscribe` CLI 显式触发。

## 一、产品目标

为个人记录流水账日记。任何时候想起来都可以对着软件说几句，晚上再系统地总结一次。

核心承诺：

- **声音必须保存**
- **语音自动转为文字**
- **每天整理成一份文字稿**（远期目标，本期不实现，详见第八章）

---

## 二、核心实体

### 2.1 草稿录音（Draft Recording）

> 用户停止录音后**先生成**的本地临时录音。

- **包含**：本地音频文件、录音开始时间、录音时长
- **特性**：仅存在于小程序本地缓存；可试听、可重录、可删除
- **生命周期**：用户点击「保存并上传」后转为 Fragment Record 并销毁；用户点击「删除」则直接销毁

### 2.2 碎片记录（Fragment Record）

> 代表「发生过的事实」，是每次说话的原始输入。

- **包含**：全局唯一 ID、录音时间、原始音频文件（MP3）、语音直转的原始文字、元数据
- **特性**：只读、只增不改；转出来的文字不管多乱，原样保留
- **来源**：由 Draft Recording 经用户确认「保存并上传」后晋升而来
- **声明**：一旦成为 Fragment Record，就只增不改，**不再真正删除**

### 2.3 每日文字稿（Daily Journal）

> 代表「整理后的日记」，是当天所有碎片记录的加工结果。**本期 MVP 不实现，仅保留概念定义供下一期使用。**

- **包含**：日期、经大模型润色排版后的通顺文字
- **特性**：可反复覆盖生成，但**必须保留所有历史版本**（追加式存储，旧版本不丢）

## 三、运作流程

### 3.1 本期 MVP 流程

```
开始录音 → 停止录音 → 草稿
                       ├── 试听 / 重录 / 删除
                       └── 保存并上传 → Fragment → 上传 OSS → 上传确认
                                                                  ↓
                                            本地脚本轮询 OSS → 下载 → Whisper 转写 → 落盘
```

1. **开始录音**：在小程序里点一下开始；录音过程中遇到锁屏、来电、微信被切后台、系统杀进程等中断事件时，**自动保存已录制部分**为草稿
2. **停止录音**：再点一下结束；支持长时间录音（单条目标 ≤ 10 分钟，超时自动分片，详见第 6.1 节）
3. **草稿阶段**：录完先生成草稿；用户可试听、重录、删除；只有点击「保存并上传」才正式生成 Fragment Record
4. **可靠上传**：晋升后的 Fragment 立即开始上传；本地缓存在「云端上传确认完成」后才允许清理（详见 7.8）
5. **本地拉取**：后端 Python 脚本按可配置的频率轮询 OSS，下载新文件（**不删除云端文件**，OSS 作为长期备份）
6. **本地转写**：用大模型将语音转写为文字，输出结构化转写结果（`transcript.json`）+ 元数据（`manifest.json`），通过文件状态机保证幂等

### 3.2 下一期流程（保留，本期不做）

```
... → 凌晨 05:00 自动整理 → 大模型润色 → 保存当日文字稿（保留历史版本）
```

## 四、设计原则

- **随时可用，方便快捷**：日常记录时必须保证极低摩擦
- **极薄前端 + 核心后端**：前端只负责采集，后端负责业务与存储
- **数据零丢失**：从录音到云端备份，每一段音频都必须有完整闭环
- **不允许虚构事实**：未来 LLM 润色阶段，**绝对禁止「添油加醋」和虚假事实**
- **不可逆性**：Fragment Record 一旦生成不可改动；只有草稿阶段才允许删改

## 六、详细需求

### 6.1 用户体验层

| # | 议题 | 决策 |
|---|---|---|
| 1 | 录音交互 | 「点一下开始、再点一下结束」，单条目标 ≤ 10 分钟 |
| 2 | 草稿模式 | 停止录音后**先生成草稿**，不立即上传；用户可试听、重录、删除 |
| 3 | 显式上传 | 用户点击「保存并上传」按钮后，草稿才晋升为 Fragment 并开始上传 |
| 4 | 录音被打断的处理 | 微信被切后台 / 锁屏 / 来电 / 系统杀进程时，**调用 `RecorderManager.onInterruptionBegin` 自动停止并保存已录制部分**为草稿；恢复后用户决定保留、丢弃或继续新录 |

| 8 | 手机端历史查看 | 不需要在手机上查看历史 Fragment 和日稿 |
| 9 | 日稿呈现方式 | 暂不确定，待后续再决定；不影响当前主流程 |

### 6.2 数据可靠性

| # | 议题 | 决策 |
|---|---|---|
| 1 | OSS 容量与积压 | 购买大容量 OSS（500G ~ 1T），允许积压；保证数据不丢 |
| 2 | 云端删除策略 | **不删除 OSS 上的文件**，本地只做下载，云端作为长期备份 |
| 3 | 去重和幂等 | 必须支持，避免重复转写（详细方案见 7.7） |
| 4 | 上传成功的定义 | 小程序上传 OSS 成功**仅是初步信号**；最终成功以 FC `/verify-upload` 确认（HeadObject 检查对象存在 + 大小匹配）为准（详见 7.8） |
| 5 | 上传成功后的本地保留 | **本地至少保留 48 小时**，无论是否完成 verify；超过 48 小时且 verify 通过才允许清理 |
| 6 | 失败重试策略 | 指数退避自动重试；**连续 3 次失败后切换为人工手动点击上传** |
| 7 | 网络差/中断兜底 | 默认确认后立刻上传；离线进队列；上传列表页面用醒目标识"未上传 N 条，距离录音已 X 小时"；**不允许长时间无网积压** |
| 8 | OSS 轮询频率 | **可配置**（默认 60 秒），通过配置文件调整，便于不同场景调试 / 节流 |
| 9 | 本地文件状态机 | 下载、转写、完成都有显式状态标记（`.part`、`.tmp`、`.done`），中断重启可恢复（详见 7.6） |

### 6.3 隐私 / 安全

| # | 议题 | 决策 |
|---|---|---|
| 1 | OSS 密钥下发方式 | **采用阿里云函数计算 FC 签发 STS 临时凭证**（详见附录 A） |
| 2 | 临时凭证授权粒度 | **每条 Fragment 单独签发**，policy 限定为只能 `PutObject` 到该 Fragment 对应的 object key；不允许写整个 Bucket（详见 7.8） |

| 6 | 多用户与登录 | 当前阶段仅自己一人使用，仅做 openid 鉴权 → **【下阶段计划 B】** 对外发布时再加完整用户系统 |

### 7.1 分层职责

| 层 | 组件 | 职责 |
|---|---|---|
| 手机端 | 微信小程序 | 录音、中断保护、草稿管理、本地缓存、调用 FC（静默登录 + 拿临时凭证）、直传音频到 OSS、调用 FC 验证上传、上传列表呈现 |

### 7.3 数据可靠性闭环

**手机端**：

- 先落盘 → 排队上传 → 上传成功并经 FC verify → 本地仍保留 48 小时 → 最终清理
- 中断事件（锁屏、来电、切后台、杀进程）→ 自动 stop 并保存已录制部分为草稿
- 上传失败 3 次 → 切换人工

**云端**：

- OSS 私有 Bucket，永久保留，不删除
- FC `/verify-upload` 给小程序「最终签收」回执

**本地**：

- 文件状态机 + 幂等判断（详见 7.6 / 7.7）保证脚本重启、转写中断后仍能正确恢复

### 7.4 文件命名规则与 ID 体系

#### 7.4.1 全局唯一 ID（Fragment ID）

每条 Fragment 在生成时分配一个**全局唯一 ID**，构成方式：

```
<YYYYMMDDTHHMMSS>_<deviceShortId>_<ulid>
```

示例：

```
20260526T144800_dev01_01HZX3K8MN5PQR9TFB7AYWVCDE
```

| 组成 | 说明 |
|---|---|
| `YYYYMMDDTHHMMSS` | 录音开始时间（本地时区），便于人眼可读、可按目录归档 |
| `deviceShortId` | 设备短 ID（小程序首次启动时生成 4-8 字符的设备指纹，持久化在本地） |
| `ulid` | 26 字符 ULID（含毫秒精度时间戳 + 随机性，单调递增、防碰撞） |

> 三段冗余的原因：人眼能直接看出"什么时间、哪台设备录的"；ULID 保证即使同一秒、同一设备多次录音也不冲突。

#### 7.4.2 长录音分片的 ID

超过单条目标时长（≥ 10 分钟）时，由前端每 N 分钟自动分片：

- 整段录音共享一个 `session_id`（同样使用 ULID）
- 每片是独立 Fragment，分别有自己的 `fragment_id`
- 在 manifest 中记录：`session_id`、`chunk_seq`（1 起）、`chunk_total`（已知时填，未知时为 null）
- UI 上多条 chunk 渲染为一段录音

#### 7.4.3 OSS 对象 Key

```
recordings/<YYYY-MM-DD>/<fragment_id>.mp3
```

#### 7.4.4 本地目录结构

```
~/SoniScope/
├── inbox/                              # 临时下载区
│   └── <fragment_id>.part              # 下载中
│
├── fragments/
│   └── 2026-05-26/
│       └── <fragment_id>/
│           ├── audio.mp3               # 原始音频（下载完成后原子写入）
│           ├── manifest.json           # 元数据（权威）
│           ├── transcript.json         # 结构化转写结果
│           ├── transcript.txt          # 纯文本（从 transcript.json 派生）
│           └── .done                   # 完成标记（最后写入）
│
├── tmp/                                # 转写工作区
│   └── <fragment_id>.transcript.json.tmp
│
└── config.yaml                         # 脚本配置（轮询周期、模型选择等）
```

  "chunk_seq": 1,
  "chunk_total": null,
  "device_id": "dev01",
  "recorded_at": "2026-05-26T14:48:00+08:00",
  "duration_seconds": 87.5,

  "audio": {
    "format": "mp3",
    "size_bytes": 1234567,
    "sha256": "abc123..."
  },

  "upload": {
    "uploaded_at": "2026-05-26T14:48:30+08:00",

> 备注：未来如引入 SQLite 索引，所有字段以 `manifest.json` 为准，SQLite 仅作为**派生只读视图**，可随时由 manifest 重建。

### 7.6 本地文件状态机

为防止 Mac 重启、脚本崩溃、转写到一半失败时残留半成品，所有文件操作遵循**先临时、后原子 rename、最后写完成标记**的三段式协议：

| 阶段 | 中间态文件 | 完成态文件 | 失败/中断的后果 |
|---|---|---|---|
| 下载 | `<fragment_id>.part` | `audio.mp3`（原子 rename）| `.part` 残留，下次轮询识别并续传 / 重下 |
| 转写 | `transcript.json.tmp` | `transcript.json`（原子 rename）| `.tmp` 残留，下次启动清理并重新转写 |
| 完成 | — | `.done` 空标记文件 | 无 `.done` 意味着流程未完整结束，需重做 |

**完成态定义**：当且仅当 `.done` 文件存在时，认为该 Fragment 已完整处理。

**启动恢复策略**：脚本启动时扫描 `~/SoniScope/fragments/**/`，对每个目录：

1. 有 `.done` → 跳过
2. 无 `.done`，但有 `audio.mp3` → 重做转写
3. 无 `audio.mp3`，有 `.part` → 视为下载中断，重下
4. 都没有 → 视为新 Fragment 待处理

### 7.7 去重与幂等设计

**为什么需要**：

- 同一 OSS 对象可能被轮询到多次（脚本重启、并发实例）
- 升级模型后可能想对存量 Fragment 重新转写，但必须是**显式操作**，不能因为改了一个配置就自动重跑全量
- 必须避免重复消耗算力

**正常轮询的幂等判断**：以 `.done` 标记文件为准

**正常轮询判断逻辑**：

1. 下载完成后计算 `audio_sha256`，写入 `manifest.json`
2. 转写前检查：该 Fragment 目录是否存在 `.done` 文件？
3. `.done` 存在 → **跳过**（无论当前配置中的模型 / 参数版本是否与 manifest 中记录的一致）
4. `.done` 不存在 → 按当前配置（模型、参数版本等）进行转写

> **设计理由**：更换模型版本（如 `large-v3` → `large-v4`）或调整参数版本是一个低频的主动决策，不应导致全量存量 Fragment 被自动重转。自动重转可能耗时数小时甚至数天，且旧的转写结果在大多数场景下仍然可用。新模型 / 新参数仅对**新进入的 Fragment** 自动生效。

**显式重转（仅通过 CLI 触发）**：

- 用户希望用新模型 / 新参数重转存量内容时，必须通过 `retranscribe` CLI 命令**显式操作**
- CLI 可利用 manifest.json 中记录的转写元数据（transcriber、model、params_version）来智能筛选"哪些 Fragment 是用旧模型转写的，需要升级"
- 支持按日期范围批量重转、支持 `--force` 强制重转
- 详见 `retranscribe` 子命令设计

**转写元数据（四元组）的用途**：

manifest.json 的 `transcription` 字段仍然记录完整的四元组：

```
(audio_sha256, transcriber_name, model_version, params_version)
```

但其用途从"正常轮询的跳过判断"变更为：

- **溯源**：记录每条 Fragment 是用什么转写器 / 模型 / 参数版本转写的
- **CLI 智能筛选**：`retranscribe --upgrade` 可通过比对 manifest 中的 model 与当前配置，自动找出"用旧模型转写的 Fragment"并批量重转
- **审计**：便于后续统计"有多少 Fragment 还在用旧模型的转写结果"

**OSS 端去重**：

- object key 本身就是全局唯一 ID，重复上传同一 key 会被视作覆盖
- 小程序在生成 fragment_id 时已经保证唯一性，不存在意外覆盖

### 7.8 上传确认协议

**问题**：`wx.uploadFile` 返回成功仅说明 HTTP 状态码 200，**不能证明 OSS 上对象真的完整存在**。

**协议设计**：

```
小程序                FC                    OSS
  │                    │                     │
  │ ① POST /issue-credential                 │
  │ ─────────────────► │                     │
  │ ◄───── STS (15min, key-scoped) ──────────│
  │                                          │
  │ ② wx.uploadFile (with STS) ─────────────►│
  │ ◄──── 200 OK ────────────────────────────│
  │                                          │
  │ ③ POST /verify-upload                    │
  │    { fragment_id, expected_sha256, size }│
  │ ─────────────────► │                     │
  │                    │ ④ HeadObject        │
  │                    │ ──────────────────► │
  │                    │ ◄── obj exists, size, etag
  │                    │                     │
  │ ⑤ { verified: true }                     │
  │ ◄───────────────── │                     │
```

**FC `/verify-upload` 内部检查项**：

- OSS 上 object 是否存在
- 文件大小是否匹配
- （可选）ETag 与小程序传来的 sha256/md5 比对

**前端动作**：

- 收到 `verified: true` → 标记 manifest，**仍保留本地 48 小时**才允许清理
- 收到失败 → 进入重传队列
- **即使不实现 `/verify-upload`，最低保障是「前端收到 OSS 200 后本地至少保留 48 小时」**

### 7.9 STS 单文件级授权

FC 签发临时凭证时，**policy 必须精确到本次要上传的那一个 object key**：

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:PutObject"],
      "Resource": [
        "acs:oss:*:*:soniscope-audio/recordings/2026-05-26/20260526T144800_dev01_01HZX3K8MN5PQR9TFB7AYWVCDE.mp3"
      ]
    }
  ]
}
```

**含义**：

- 拿到这份临时凭证只能上传这一个文件
- 不能列 Bucket、不能读其他文件、不能上传到别的 key
- 凭证 15 分钟过期

### 7.10 FC 接口鉴权

**目的**：FC 接口（`/issue-credential`、`/verify-upload`）暴露在公网，**绝不能允许匿名调用**。

**方案**：基于微信小程序静默登录（jscode2session）：

```
小程序                          FC                 微信开放接口
  │ wx.login() → code            │                    │
  │ ─────────────────────────►   │                    │
  │                              │ jscode2session     │
  │                              │ ─────────────────► │
  │                              │ ◄── openid, session_key
  │                              │                    │
  │                              │ openid in allowlist?
  │                              │ - 是 → 签发凭证    │
  │                              │ - 否 → 403 拒绝    │
  │ ◄──────── 凭证 / 403 ────────│                    │
```

**openid allowlist 维护**：

- 本期：FC 环境变量里硬编码自己的 openid（一个）
- 下一期（计划 B）：迁移到配置表 / 数据库支持多用户

## 附录 A · 函数计算 FC + STS 实施流程概要

> 详细操作指引在动手实施时再展开，这里仅保留架构与步骤备忘。

### A.1 名词解释

| 名词 | 是什么 |
|---|---|
| **RAM 用户** | 阿里云子账号，类似"二级管理员"，可以单独授权 |
| **AccessKey (AK/SK)** | 一对长期密钥，权限大，**绝对不能放进小程序** |
| **STS** | 阿里云的"临时凭证签发服务"，签发 15 分钟 ~ 1 小时有效的临时密钥 |
| **临时凭证** | 短期 AccessKey + SecretKey + SecurityToken 三件套，过期就废，泄露损失小 |
| **函数计算 FC** | 阿里云的 Serverless 服务，部署一段函数代码，给它一个 HTTPS URL，外部一调用就执行 |
| **openid** | 微信用户在某个小程序下的唯一标识，通过 `wx.login` + `jscode2session` 获得 |

### A.2 实施清单

1. 开通阿里云账号 + 实名认证 + 充值
2. 开通 OSS，创建私有 Bucket（如 `soniscope-audio`）
3. RAM 创建专用子账号（仅授 `AliyunSTSAssumeRoleAccess`）
4. RAM 创建角色，权限策略限定为只能 `oss:PutObject` 到指定 Bucket 路径前缀
5. 开通函数计算 FC，部署两个函数：
   - `/issue-credential`：校验 openid → 调用 STS 签发**精确到 object key**的临时凭证
   - `/verify-upload`：对 OSS 做 HeadObject 校验
6. FC 配置 HTTP 触发器，得到自带 HTTPS 域名；将该域名 + OSS Bucket 域名加入微信小程序合法域名白名单
7. 小程序：`wx.login` → 调 FC 校验 → 拿临时凭证 → `wx.uploadFile` 直传 OSS → 调 FC verify
8. 本地 Python 脚本：用长期只读 AK 轮询 OSS → 下载 → Whisper 转写 → 按状态机落盘

| STS 调用 | ¥0（免费）|

| 本地 Whisper | ¥0（自有硬件）|
| **合计** | **~¥120/月** |
