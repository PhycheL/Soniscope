## 上线判定口径

### Q1: BLOCKER/PRE-LAUNCH/POST-LAUNCH 判定规则怎么定?

| Option | Description | Selected |
|--------|-------------|----------|
| 先定判定准则再逐条套(推荐) | 三级准则写进报告,每条判定引准则+一句理由,与严重度独立评 | ✓ |
| 严重度映射+例外清单 | 与"严重度≠紧迫度"要求贴合度低 | |

### Q2: 判定准则里的"上线"指什么场景?

| Option | Description | Selected |
|--------|-------------|----------|
| 个人自用正式化(allowlist 不开放) | 判定重心:数据不丢、静默失败可发现;滥用类权重低 | |
| 小范围真实用户(allowlist 扩容) | 邀请制加人,非作者用户无法自救;增加用户可感知卡死态权重 | ✓ |
| 未来公开可能,按保守口径 | 频控/滥用类不降权,可能把不必要项抬进 PRE-LAUNCH | |

### Q3: RPT-01 总体上线判定由谁出、什么形态?

| Option | Description | Selected |
|--------|-------------|----------|
| 报告推导结论,三档词(推荐) | 有 BLOCKER→NO-GO;无 BLOCKER 有 PRE-LAUNCH→CONDITIONAL GO;全 POST-LAUNCH→GO | ✓ |
| 报告只给依据,用户拍板 | 总判定栏留占位,报告交付时不自包完整 | |

### Q4: 逐条判定结果要不要批量呈报批准?

| Option | Description | Selected |
|--------|-------------|----------|
| 准则批准+结果抽样呈报(推荐) | 准则先批;呈报非平凡项(全部 BLOCKER+PRE-LAUNCH、与严重度直觉相厄项) | ✓ |
| 全部 40 条判定一次呈报 | 最可控但审阅量大 | |
| 准则批准后全信任 | PRE-LAUNCH 清单无事前把关 | |
