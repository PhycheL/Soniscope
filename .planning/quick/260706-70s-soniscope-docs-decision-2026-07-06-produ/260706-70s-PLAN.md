【决策背景（2026-07-06）】
用户在上线审计阶段对 SoniScope 提出根本性质疑：flomo 已能满足需求（语音输入、MCP 对外提供资料、内容导出），个人再开发此程序是否有必要。

【决策过程 · 第一轮：SoniScope vs flomo 表面重叠分析】
- 结论：两者仅表面重叠（都能语音变文字）。SoniScope 文档（PRD §1）的核心承诺是"说出口的话 100% 落到云端音频 + 本地文本，不丢、不重、不虚构"。
- 三个 flomo 不具备的差异点：① 原始音频是第一资产（OSS 永不删除 FR-11/R-07、retranscribe --upgrade 全量重转）；② 数据主权（本地 audio.wav + transcript.json，自有 OSS 桶）；③ 长录音流水账场景（25 分钟自动分片、中断保护）。
- 诚实的反方：当前 MVP 交付物体验原始（NG-1/NG-2 不做 LLM 整理与呈现界面）；持续成本真实（本地 Worker 常驻、NLS 无免费额度、FC/OSS 运维）；单人项目 bus factor。
- 发现：docs/multi-user-design.md 的多用户/对外发布方向与个人工具定位冲突，属于该砍的部分。

【决策过程 · 第二轮：用户的关键反思（转折点）】
- 用户明确："语音不是重点，语音的内容才是重点"；真实需求是"随时以最低摩擦记录思考和体悟"（capture）；视频/音频日记需求推迟（"那时再说"）。
- 这一反思抽掉了 SoniScope 的地基：音频资产、数据主权两大差异点的价值前提消失。SoniScope 剩下的只是"比 flomo 摩擦更大的语音转文字管道"。
- capture 环节恰是 flomo 最强、SoniScope 最弱之处（转写延迟 + 无呈现界面对"记录思考"接近致命）。

【决策过程 · 第三轮：新架构确认】
- 用户提出并获确认："flomo 作为记录入口 → 自建第二大脑系统（尚未启动）作为下游"。
- 该方案的关键优点：优雅降级——即使第二大脑永不启动，flomo 独立成立；而 SoniScope 只有整条流水线跑通才产生价值。

【最终判断】
SoniScope 作为产品可以停止——不是烂尾，而是需求被重新定义后，它解的已不是用户的问题。

【待验证的承重假设】
flomo 的数据出口能力：MCP/API 能否程序化读取全量 memo（含标签与时间戳），还是只能手动快照导出。手动导出是可接受摩擦但需知情接受。

【对未来的建议（四条，逐条成文）】
1. 第二大脑不耦合 flomo：先定义摄入契约（纯文本 + 时间戳 + 标签的最小格式），flomo 只是适配器之一，入口工具随时可换。
2. 视频/音频日记需求出现时，以"新适配器"形式接入，不复活本仓库；届时技术起点参考 docs/fc-transcribe-design.md（FC 直转已证明比本地 Worker 简单得多）。
3. 仓库处置：停掉上线审计里程碑；冷冻而非删除（打 tag 归档 + closure note）；保留可复用资产——① 已验证的"OSS 签名 URL → NLS filetrans"转写链路与 STS 单 key 签发模式；② docs/audit-methodology.md 审计方法论。
4. 关停阿里云 FC 函数与本地 Worker，止住 NLS 按量计费与资源闲置。
